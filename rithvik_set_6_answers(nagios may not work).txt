1. DOCKER – WORDPRESS + MYSQL DIGITAL LIBRARY
======================================================

AIM
To deploy a WordPress digital library using separate WordPress and MySQL containers, connect them through a custom Docker network, and preserve data using named volumes.

REQUIREMENTS
- Docker Engine
- Docker Compose plugin
- Internet connection

STEP 1 – Verify Docker
---------------------
docker --version
docker compose version

If Docker is not installed, install Docker Engine and the Compose plugin using the official Docker instructions for your Ubuntu version.

STEP 2 – Create a project directory
-----------------------------------
mkdir docker-library
cd docker-library

STEP 3 – Create compose.yaml
----------------------------
Create a file named compose.yaml and add:

services:
  db:
    image: mysql:8.0
    container_name: library-db
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ChangeThisRootPassword
      MYSQL_DATABASE: library
      MYSQL_USER: libraryuser
      MYSQL_PASSWORD: ChangeThisUserPassword
    volumes:
      - mysql_data:/var/lib/mysql
    networks:
      - library-network
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost", "-pChangeThisRootPassword"]
      interval: 10s
      timeout: 5s
      retries: 10
      start_period: 30s

  wordpress:
    image: wordpress:latest
    container_name: library-wordpress
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db:3306
      WORDPRESS_DB_USER: libraryuser
      WORDPRESS_DB_PASSWORD: ChangeThisUserPassword
      WORDPRESS_DB_NAME: library
    volumes:
      - wordpress_data:/var/www/html
    networks:
      - library-network

volumes:
  mysql_data:
  wordpress_data:

networks:
  library-network:
    driver: bridge

NOTE:
- Change the example passwords before using this outside a lab.
- This Compose file creates a private network and named volumes automatically.
- The database port is not published to the host. WordPress reaches MySQL using the service name db.
- The health check and depends_on condition help prevent WordPress from starting before MySQL is ready.

STEP 4 – Start both containers
------------------------------
docker compose up -d

STEP 5 – Check containers
-------------------------
docker compose ps
docker ps

STEP 6 – View logs
------------------
docker compose logs
docker compose logs db
docker compose logs wordpress

STEP 7 – Open WordPress
-----------------------
Open this address in a browser:

http://localhost:8080

Complete the WordPress setup. You can create sample digital-library pages and posts.

STEP 8 – Verify network
-----------------------
docker network ls
docker network inspect docker-library_library-network

The exact Compose-generated network name may be prefixed by the project directory name.

STEP 9 – Verify persistent volumes
----------------------------------
docker volume ls
docker volume inspect docker-library_mysql_data
docker volume inspect docker-library_wordpress_data

STEP 10 – Test recovery after deleting a container
--------------------------------------------------
docker compose stop db
docker compose rm -f db

Recreate the database container using the same Compose configuration and volume:

docker compose up -d db
docker compose ps
docker compose logs db

The MySQL data is stored in the named volume, not in the container's writable layer. Removing the container does not remove the named volume. Do NOT run "docker compose down -v" if you want to keep the data; the -v option removes Compose-managed volumes.

USEFUL COMMANDS
---------------
Stop containers but keep data:
docker compose stop

Start them again:
docker compose start

Stop and remove containers/network but keep named volumes:
docker compose down

Remove containers AND named volumes (DELETES STORED DATA):
docker compose down -v

EXPECTED RESULT
---------------
- MySQL container is running and healthy.
- WordPress container is running.
- WordPress opens at http://localhost:8080.
- WordPress can communicate with MySQL through the private Docker network.
- MySQL and WordPress files persist in named volumes.

SCENARIO QUESTIONS
------------------
Q1. What happens if the MySQL container crashes?
Answer:
WordPress may show a database connection error because it cannot reach MySQL. Check logs using "docker compose logs db". Restart it using "docker compose restart db". If the container was removed, recreate it with "docker compose up -d db". The named volume preserves the database files, assuming the volume itself was not deleted or corrupted.

Q2. How can data be recovered after deleting a container?
Answer:
Docker named volumes exist independently of containers. Recreate the database container while mounting the same volume. For this example, the volume is mysql_data. Do not delete it with "docker compose down -v". Backups are still required for protection against disk failure or corruption.

Q3. Why use a custom Docker network?
Answer:
A custom bridge network lets containers communicate by container/service name, isolates this application stack from unrelated containers, and avoids exposing the database port to the host unnecessarily.

Q4. How can MySQL security be improved?
Answer:
Use strong unique passwords, do not expose port 3306 publicly, use a restricted application user instead of root, limit network access, keep images updated, use secrets rather than committing passwords, and back up the database securely.

Q5. How can five department websites be hosted?
Answer:
Run separate WordPress services for each department, with separate databases or database schemas and separate persistent volumes. Put a reverse proxy such as Nginx in front and route different hostnames/subdomains to the corresponding WordPress service. Use separate credentials and restrict database access.

SCENARIO QUESTIONS

Q1. What happens if compilation errors occur?
Answer:
Maven compilation fails and returns a non-zero exit status. Jenkins marks the build as FAILED. The developer checks Console Output, fixes the Java source, commits and pushes the correction, and runs the build again.

Q2. What happens if compilation succeeds but tests fail?
Answer:
The compile phase succeeds, but the test phase reports failures. Maven exits unsuccessfully and Jenkins marks the build as FAILED. Developers inspect the test report, correct the code or tests, and rerun the pipeline.

Q3. Why use Maven instead of manually creating JAR files?
Answer:
Maven provides a standard project structure, dependency management, repeatable builds, compilation, testing, packaging, and integration with CI tools. Manual JAR creation is more error-prone and does not automatically manage dependencies or tests.

Q5. Difference between CI and CD?
Answer:
Continuous Integration (CI) automatically integrates code changes and builds/tests them frequently. Continuous Delivery (CD) automates preparation of software for release. Continuous Deployment goes further by automatically deploying every change that passes the required checks.

3. KUBERNETES – MINIKUBE DEPLOYMENT, SCALING AND ROLLBACK
======================================================

AIM
To deploy an application in Minikube, maintain two or more replicas, expose it through a Service, scale it from two to five replicas, and demonstrate rolling update and rollback.

REQUIREMENTS
- Docker
- Minikube
- kubectl

IMPORTANT
The following Nginx workload is a simple, reliable web-server demonstration of Kubernetes Deployment and Service operations. It is not the Java console program in the supplied GitHub repository. That Java program is not an HTTP web server.

STEP 1 – Verify tools
---------------------
docker --version
minikube version
kubectl version --client

STEP 2 – Start Minikube
-----------------------
minikube start --driver=docker

Check:
minikube status
kubectl get nodes

If kubectl is not installed locally, Minikube can run it:
minikube kubectl -- get pods -A

STEP 3 – Create a Deployment with two replicas
----------------------------------------------
kubectl create deployment library-app --image=nginx:1.27 --replicas=2

Check:
kubectl get deployments
kubectl get pods -o wide

STEP 4 – Expose the Deployment
------------------------------
kubectl expose deployment library-app --type=NodePort --port=80

Check:
kubectl get services

STEP 5 – Open the application
-----------------------------
minikube service library-app

Minikube opens the service URL. If automatic browser opening is unavailable, run:
minikube service library-app --url

STEP 6 – Scale from two to five replicas
----------------------------------------
kubectl scale deployment library-app --replicas=5

Verify:
kubectl get deployment library-app
kubectl get pods

The desired and ready replica counts should eventually become five.

STEP 7 – Demonstrate self-healing
---------------------------------
List pods:
kubectl get pods

Delete one pod (replace POD_NAME with an actual pod name):
kubectl delete pod POD_NAME

Check again:
kubectl get pods

The Deployment's ReplicaSet controller creates a replacement pod to maintain the desired replica count.

STEP 8 – Perform rolling update
-------------------------------
kubectl set image deployment/library-app nginx=nginx:1.28

Check:
kubectl rollout status deployment/library-app
kubectl rollout history deployment/library-app
kubectl get pods

STEP 9 – Roll back
------------------
kubectl rollout undo deployment/library-app

Verify:
kubectl rollout status deployment/library-app
kubectl rollout history deployment/library-app
kubectl describe deployment library-app

STEP 10 – Clean up after the practical
--------------------------------------
kubectl delete service library-app
kubectl delete deployment library-app
minikube stop

EXPECTED RESULT
---------------
- Minikube cluster starts successfully.
- Deployment creates two replicas.
- Service exposes the Nginx application.
- Scaling command increases replicas to five.
- Deleting a pod causes a replacement pod to be created.
- Rolling update changes the image.
- Rollback returns to the previous Deployment revision.

SCENARIO QUESTIONS
------------------
Q1. What happens if a pod crashes?
Answer:
The ReplicaSet controller notices that the actual number of pods is below the desired number and creates a replacement pod. This is Kubernetes self-healing.

Q2. What is the purpose of desired replicas?
Answer:
The replica count tells Kubernetes how many pod instances should be maintained. If five replicas are desired, Kubernetes continuously tries to keep five matching pods running.

Q3. Difference between manual and automatic scaling?
Answer:
Manual scaling is performed by an administrator, for example with "kubectl scale deployment library-app --replicas=5". Automatic scaling uses a Horizontal Pod Autoscaler (HPA) and configured metrics such as CPU utilization to adjust replicas. HPA requires metrics to be available and resource requests to be configured appropriately.

Q4. Why use a Kubernetes Service?
Answer:
Pods are replaceable and their IP addresses can change. A Service provides a stable virtual IP/DNS name and routes traffic to matching healthy endpoints. NodePort exposes a service through a port on cluster nodes.

Q5. How can a failed update be recovered?
Answer:
Use:
kubectl rollout undo deployment/library-app
Then verify:
kubectl rollout status deployment/library-app

4. NAGIOS – HOST AND SERVICE MONITORING
======================================================

AIM
To run Nagios Core in a Docker container, access its monitoring dashboard, and explain how host and service checks monitor availability and resource thresholds.

REQUIREMENTS
- Docker Engine
- Internet connection
- Browser

STEP 1 – Pull Nagios image
--------------------------
docker pull jasonrivers/nagios:latest

This image provides Nagios Core and bundled monitoring components.

STEP 2 – Run Nagios container
-----------------------------
docker run -d \
  --name nagios \
  --restart unless-stopped \
  -p 8080:80 \
  jasonrivers/nagios:latest

STEP 3 – Check container
------------------------
docker ps
docker logs nagios

STEP 4 – Open dashboard
-----------------------
Open:
http://localhost:8080

Default credentials documented by the image:
Username: nagiosadmin
Password: nagios

Change/default credentials must be secured before exposing the dashboard beyond a private lab machine. Do not expose this example dashboard publicly with default credentials.

STEP 5 – Understand host and service checks
--------------------------------------------
Nagios uses plugins to run checks and return status:
- OK
- WARNING
- CRITICAL
- UNKNOWN

Examples of checks used in a Nagios setup:
- check_ping: host/network reachability
- check_http: HTTP response
- check_disk: disk usage
- check_load: system load
- NRPE/NCPA or another agent: remote host resource checks

IMPORTANT HOST-MONITORING LIMITATION
-----------------------------------
A Nagios process running inside Docker does not automatically see all the host machine's CPU, memory, processes and disk state as if it were installed directly on the host. The Docker image gives you a running Nagios server/dashboard. For real remote host CPU, memory and disk monitoring, configure a monitoring agent such as NRPE or NCPA on the target host and configure Nagios to query it. Configure service checks for HTTP and database endpoints separately.

STEP 6 – Example service-check definitions
------------------------------------------
Nagios object definitions are normally placed in the Nagios configuration directory and must reference valid host and command definitions. A typical HTTP service concept is:

define service {
    use                     generic-service
    host_name               library-server
    service_description     HTTP
    check_command           check_http
}

This example is illustrative: the host "library-server", generic-service template and check_http command must exist in the actual configuration before Nagios can load it. After editing configuration, validate it using the Nagios binary's configuration verification option, then reload/restart Nagios according to the image's documentation.

STEP 7 – Useful Docker commands
-------------------------------
docker logs nagios
docker exec -it nagios sh
docker restart nagios
docker stop nagios
docker start nagios

STEP 8 – Demonstrate alert conditions
-------------------------------------
In a configured Nagios environment:
- Set a warning threshold for a resource.
- Set a higher critical threshold.
- Run or schedule the relevant plugin check.
- Confirm the service changes from OK to WARNING or CRITICAL when the threshold is crossed.
- Restore normal conditions and confirm recovery to OK.

Do not claim CPU/memory/disk monitoring is configured merely because the dashboard opens. The relevant host agent, host/service definitions, plugin commands and thresholds must be configured.

EXPECTED RESULT
---------------
- Nagios container is running.
- Dashboard opens at http://localhost:8080.
- Login succeeds using the documented default credentials in a local lab.
- Host/service monitoring is demonstrated after the appropriate checks and agents are configured.

SCENARIO QUESTIONS
------------------
Q1. How does Nagios detect high CPU usage?
Answer:
Nagios runs a load or CPU monitoring plugin at scheduled intervals. The plugin compares measured values with configured warning and critical thresholds and returns a status. For remote systems, an agent such as NRPE/NCPA may provide the resource data.

Q2. Difference between WARNING and CRITICAL?
Answer:
WARNING means a configured warning threshold has been crossed and attention may be needed. CRITICAL means the critical threshold has been crossed or the service is unavailable. The exact thresholds depend on the check configuration.

Q3. What if the application fails but the server is running?
Answer:
A host ping check may still report the server as reachable, while an HTTP or application-specific service check reports failure. Host availability and application availability are different checks.

Q4. What if the Nagios server itself fails?
Answer:
Nagios cannot reliably report its own outage if the monitoring engine is down. Use a separate monitoring system/server or an external uptime monitor to monitor the Nagios host and dashboard.

Q5. How can Tomcat, MySQL and network failures be distinguished?
Answer:
- Network failure: ping/connectivity check fails or the target cannot be reached.
- Tomcat/application failure: host is reachable but HTTP/Tomcat check fails.
- MySQL failure: database port or authenticated database check fails.
Use multiple checks and inspect their results rather than relying on one ping test.

5. AWS EC2 – DEPLOYING THE LIBRARY MANAGEMENT PROJECT
======================================================

AIM
To launch an EC2 instance, connect securely through SSH, install Java, transfer and run the Java Library Management JAR, configure security rules, and monitor the instance.

VERY IMPORTANT REPOSITORY LIMITATION
------------------------------------
The supplied GitHub repository is a Java console application packaged as a JAR. It is NOT a Java web application packaged as a WAR. It does not currently contain a Tomcat web application or a browser endpoint. Therefore the actual repository can be run on EC2 through SSH as a console program. It cannot be made browser-accessible just by copying it to Tomcat.

If the practical examiner specifically requires a browser-based Tomcat application, the application must first be developed/converted as a web application and packaged as a WAR, or a separate web-server demo must be used. Do not claim the current JAR is a WAR.

STEP 1 – Launch EC2
-------------------
1. Sign in to AWS Management Console.
2. Open EC2 > Instances > Launch instances.
3. Give the instance a name, for example Library-Management.

5. Choose an instance type suitable for the lab and check current pricing/free-tier eligibility.
6. Create or select an SSH key pair and download the private key.

STEP 2 – Configure security group
---------------------------------
For the console-JAR deployment:
- SSH TCP port 22: source should be My IP only.

BROWSER ACCESS CLARIFICATION
----------------------------

SCENARIO QUESTIONS
------------------
Q1. Why might an application not be accessible through a browser?
Answer:
Possible causes include an incorrect public IP/DNS name, blocked security-group or OS firewall port, application process stopped, wrong listening port, incorrect URL/context path, failed deployment, or the application not being a web application at all. In this repository's case, the last point applies: it is a console JAR, not a web server.

Q2. How can SSH access be restricted?
Answer:
Allow TCP port 22 only from trusted IP addresses (My IP), use key-based authentication, protect the private key, disable password login where appropriate, and avoid 0.0.0.0/0 for SSH.

Q3. What if Tomcat stops but EC2 is still running?
Answer:
The EC2 virtual machine can remain healthy while the web application is unavailable. Check Tomcat's service/process and logs, then restart it using the appropriate service or startup command. This applies only when a Tomcat web application has actually been installed.

Q4. How can application availability be improved?
Answer:
Run multiple application instances across multiple Availability Zones, use an Application Load Balancer with health checks, configure Auto Scaling, monitor application health, use backups, and avoid a single database or server as a single point of failure.

Q5. Why use an Application Load Balancer with multiple EC2 instances?
Answer:
An ALB distributes HTTP/HTTPS traffic across registered targets, performs health checks, and can stop routing traffic to unhealthy targets. Multiple EC2 instances improve capacity and fault tolerance compared with one instance, especially when placed across multiple Availability Zones.
